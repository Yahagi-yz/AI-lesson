Lesson 0007 · CONTEXT.md vs ADR：Two Artifacts, Two Bars

单一目标：面对一个已经明确的陈述，判断它应该写进领域 glossary、值得记录为 ADR，还是根本不该进入这两类持久化文档。

速查：Two Write Bars 上一课 课程地图
本课完成标志

你能把“概念是什么”路由到 CONTEXT.md；把真正重要且需要保留理由的决策路由到 ADR；把普通实现细节、易逆转策略和显然选择挡在两者之外。

1. 同一个 domain-modeling，两个不同容器

一个陈述已经澄清 ↓ 它在定义领域概念 / 领域关系？ ├─ Yes → CONTEXT.md └─ No ↓ 它是一个“值得未来人记住为什么”的决策？ ├─ 三个 ADR gate 全通过 → ADR └─ 任一 gate 不通过 → 两边都不写

CONTEXT.md 保存语言；ADR 保存高价值决策的“为什么”。不要把两者都变成项目流水账。

2. CONTEXT.md 的 bar：这是项目领域里的“词”吗？

Lesson 0006 已经证明：CONTEXT.md 是 glossary。它保存项目特有领域概念的定义与关系，而不是数据库、函数、API、重试次数或开发计划。

适合 CONTEXT.md Task: A unit of work that may have multiple Runs. Run: One concrete execution attempt of a Task.

3. ADR 的 bar 更高：三个 gate 必须全部通过

Gate 1 — Hard to reverse? 改变它的代价是否显著？ ↓ yes Gate 2 — Surprising without context? 未来的人看到代码，会不会问“为什么这么做？” ↓ yes Gate 3 — Real trade-off? 是否真的比较过可行替代方案，并因具体理由做了取舍？ ↓ yes ADR 任何一个 no → Skip ADR

ADR 不是“所有 decision 的日志”。官方甚至强调应当 offer sparingly：三项缺一项就跳过。

4. 三种内容不要混

领域定义 “Run 是 Task 的一次具体执行。” → CONTEXT.md 高价值决策 “Ordering 与 Billing 用 domain events，而不是同步 HTTP， 因为要隔离故障并允许独立扩缩；迁移通信模式代价很大。” → ADR（若三个 gate 均成立） 普通实现/策略 “失败自动重试 3 次。” “函数叫 run_task()。” → 通常 Neither：去 spec / config / code / runbook 等合适位置

5. 为什么“是 decision”仍然可能不写 ADR？

因为 ADR 的目的不是证明“我们讨论过”，而是防止未来的人在缺少上下文时误解或重新打开一个代价高的取舍。

决定：按钮文案从“Run”改成“Execute” 可轻易改回 → Gate 1 fail → 不写 ADR 决定：沿用仓库已有 JSON 库 没有真实替代取舍 → Gate 3 fail → 不写 ADR 决定：核心写模型采用 event sourcing 而非 CRUD 昂贵迁移 + 未来会疑惑 + 有真实替代方案 → 可能值得 ADR

“这是一个决定” ≠ “这是一个 ADR”。ADR 是经过三道 gate 的少数决定。

6. Retrieval practice

每题都在三类里选：术语表 / 决策档 / 都不写。

Q1. “Run 是 Task 的一次具体执行；一个 Task 可以有多个 Runs。”
Q2. “核心订单写模型采用 event sourcing 而非 CRUD；团队比较过两者，因为审计与历史重放要求接受了更高复杂度，未来迁移成本很高。”
Q3. “Worker 失败后最多自动重试 3 次。”
Q4. “继续使用仓库已经安装的 JSON parser，因为它现成可用；没有讨论其他方案。”
Q5. “Customer 数据只由 Customer context 拥有；其他 context 只能保存 CustomerId。我们放弃共享表以避免跨域耦合，迁移这个边界代价很大。”

7. 一句话记忆

“是什么” → CONTEXT.md；“为什么选这个高成本方案”且三 gate 全过 → ADR；其余不要硬塞进这两个文件。
