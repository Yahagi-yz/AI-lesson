Lesson 0006 · domain-modeling：把模糊词磨成 Ubiquitous Language

单一目标：当项目里的“词”开始含义不一致时，能识别这是 domain-modeling 问题，并用 concrete scenario / edge case 把它收敛成 canonical term。

速查：Language Loop 上一课 课程地图
本课完成标志

你能发现模糊、重载或冲突术语；不替用户暗选含义；用具体场景逼清边界；术语确定后知道什么可以写进 CONTEXT.md。

1. 什么时候“词”本身就是工程问题？

假设项目里到处都有 account：

产品说 account = 付费客户公司 登录代码说 account = 登录用户 账单代码说 account = 结算对象

这时问题不是“选哪个变量名好看”，而是团队对领域概念没有共享边界。官方 domain-modeling 的职责就是主动挑战这种模糊、重载或与既有 glossary 冲突的语言。

Ubiquitous language 不是术语装饰，而是：同一个 canonical term 在团队、对话、代码和文档里稳定指向同一个领域概念。

2. 不要替用户偷偷选一个含义

AI 最危险的做法是看到 account 后自己猜：“大概就是用户吧。”正确动作是把冲突显式化，并提出更精确的候选：

“你这里说 account， 是指 Customer（付费主体）， 还是 User（登录并操作系统的人）？ 这两个概念目前混在一起了。”

领域模型的价值不在“高级名词”，而在消灭这种静默歧义。

3. Concrete scenario 是边界显微镜

只问“Customer 和 User 有什么区别？”容易得到空泛定义。更有效的是制造一个具体场景：

场景 A：一家公司买了服务，但有 3 个员工登录。 → 这是 1 个 Customer + 3 个 Users？ 场景 B：一个员工离职，但公司订阅仍然存在。 → 删除 User 是否应该影响 Customer？ 场景 C：同一个 User 能否属于两个 Customers？ → 如果可以，关系边界又是什么？

这些 edge cases 会迫使模型从“听起来差不多”走向“边界真的说得清楚”。

4. 代码和语言冲突时，不能静默选边

如果用户说“Order 可以部分取消”，但代码只支持整单取消，domain-modeling 应把矛盾摆出来，而不是默认用户对，也不是默认代码对。

用户语言：partial cancellation exists 代码事实：cancel(orderId) cancels whole Order ↓ 明确指出冲突 ↓ 用具体场景确认真正领域规则 ↓ 再决定语言或代码哪边需要改变

5. 术语一旦确定，就立即写入 glossary

CONTEXT.md 的角色非常窄：glossary and nothing else。它定义“一个东西是什么”，而不是“代码怎么实现”。

**Customer**: A person or organization that buys the service. _Avoid_: account, client **User**: An authenticated person who operates within a Customer. _Avoid_: account, login

下面这种内容则不应该进入 glossary：

User 存在 PostgreSQL users 表 主键使用 UUID 登录接口走 /api/v2/auth 下一步要把缓存迁到 Redis

CONTEXT.md 定义领域概念；spec / implementation details / scratch notes 不属于这里。

6. Retrieval practice

Q1. “account”在产品文档里指公司，在认证代码里指登录用户。当前最直接的问题？
Q2. Customer 和 User 的关系仍然说不清。domain-modeling 下一步最好做什么？
Q3. 用户说支持部分取消，但代码只会整单取消。正确动作？
Q4. 哪个内容最适合写进 CONTEXT.md？
Q5. AI 只是读取已有 CONTEXT.md 来沿用项目词汇，这本身算 domain-modeling 吗？

7. 一句话记忆

词有歧义 → 不猜 → 用 scenario 压边界 → 与代码/现有 glossary 核对 → 定 canonical term → 立即写入 glossary。

ADR 也是 domain-modeling 的一部分，但它有另一套更高的写入门槛；本课先只掌握“语言收敛”这条回路。
