真实工程场景：失败分析任务的“恢复”

你维护一个已有仓库 bioflow-runner，用于执行内部生信分析流程。产品提出：

“失败的分析流程要支持从最后一个成功步骤继续。 用户看到的仍然应该是同一个分析任务， 但审计历史不能乱。 先把方案问清楚，不要开始写实现代码。”

AI 已经从仓库查到的状态

CONTEXT.md

Analysis Task：用户提交的一项逻辑分析工作。

Run：某个 Analysis Task 的一次具体执行；一个 Task 可以有多个 Runs。

Step Result：成功 Step 产生的不可变结果。

代码 / 数据库 - retry_run()：失败后创建一个新的 Run，并从头计算全部 steps - runs.id：不可变主键 - step_results：归属于具体 run_id - 当前没有 resume endpoint 已有 ADR - Run identity 保持不可变，用于 audit / replay - 当时明确放弃“失败后继续修改同一个 Run” - 若推翻该决定，会影响 scheduler、audit、replay 与数据迁移 当前语言 - UI 写 “Retry” - SOP 写 “rerun” - 产品 brief 写 “resume” - 团队口头上三者经常混用

还有两项仓库事实尚未查完：

F1. 新 Run 是否能安全复用旧 Run 的 Step Result， 包括 provenance / checksum / artifact ownership 约束？ F2. 用户点击“恢复”时，输入数据、参数或流程版本 是否可能已经变化？现有代码如何处理这些变化？

AI 当前准备这样做

A. 先把 CONTEXT.md 改成： “Resume = 在原 Run 上从失败 Step 继续执行。” B. 问用户： “数据库现在能不能给 failed Run 继续追加 step？” C. 第一轮同时问： Q1. Resume 应保留原 Run ID，还是创建新 Run？ Q2. 如果创建新 Run，是否复用旧 Run 的成功 Step Result？ Q3. 如果输入或参数变化，哪些旧 Step Result 还能复用？ Q4. Cancelled Run 是否也允许恢复？ Q5. UI 按钮最终叫 Resume、Retry 还是 Rerun？ D. 因为已有 retry_run()，AI 先创建一个 ADR： “Resume 采用新 Run。” E. 同时开始写 resume endpoint 和数据库 migration， 等用户回答后再补细节。

你的验收回答

不要只给结论。尽量说明“为什么现在能问 / 为什么必须后置 / 为什么属于 fact 或 decision / 为什么写或不写 durable docs”。
